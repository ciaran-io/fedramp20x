## Purpose

The company knows what it runs, keeps its policies current and has executive backing for security.

## Scope

All Orrinwick staff and contractors, and every information resource marked in scope in mas/mas-record.json.

This policy covers these information resources from the scope record:

| ID | Resource |
|---|---|
| N3 | Security and compliance team |
| N4 | Security policies and procedures |
| E1 | Source control (hosted) |
| E5 | Vulnerability scanning and dependency analysis |
| P1 | Production cloud accounts and network |

## Requirements

| ID | Requirement | KSIs |
|---|---|---|
| PIY-1 | The inventory of in-scope resources is generated from the scope record and checked against live state. A live resource with no scope ID is a finding. | KSI-PIY-GIV |
| PIY-2 | The executive team reviews security status, risks and policy exceptions every quarter. The review is minuted. | KSI-PIY-RES |
| PIY-3 | The executive team reviews security spending against the risk register each year. | KSI-PIY-RIS |
| PIY-4 | Security requirements are part of each stage of the software development lifecycle. Design review, code review and dependency scanning are required for every release. | KSI-PIY-RSD |
| PIY-5 | Orrinwick publishes a vulnerability disclosure route, answers reports within 3 business days and tracks each report to closure. | KSI-PIY-RVD |
| PIY-6 | The GRC Lead reviews every policy in this set at its stated cadence and records the review date. | KSI-PIY-RES |

## Exceptions

An exception needs a written request, a named risk owner, a compensating control and an expiry date of no more than 90 days. The GRC Lead records approved exceptions in docs/security-decision-record.md. An expired exception is a policy violation.

## Enforcement

Violations are reported to the GRC Lead. Staff violations follow the personnel security process (N5).
